# OttoRestart

OttoRestart is an isolated Next.js, FastAPI, and PostgreSQL application for detecting and reviewing OTTO 3M/12M restrictions. The public base path is `/restart`; the database, queue, and credentials are separate from OttoFlow.

The backend defaults to `LEGACY_READ_ONLY`. DEMO is explicit and isolated. OTTO/Aftercool/OpenAI reads, background workers, discovery scheduling, and all product/availability writes are disabled by default. Publication is not enabled; an accepted HTTP request or queue status is never treated as proof of ONLINE.

## Авторизация (Login / Password)

Доступ к разделам `/restart/*` защищён сессией по логину и паролю. Для нескольких общих операторских входов запускайте `python3 scripts/create_login.py`; пароли сохраняются как PBKDF2-хеши в `.env`. Ролей нет: каждый настроенный вход имеет одинаковые права и общий набор доступных JV/XL аккаунтов.
- Для одного legacy-входа поддерживаются `OTTORESTART_AUTH_USER` и `OTTORESTART_AUTH_PASSWORD`; карта из `OTTORESTART_AUTH_USERS_B64` имеет приоритет. Сессии подписывает отдельный `OTTORESTART_AUTH_SECRET`.
- BFF передаёт backend краткоживущий (60 секунд) подписанный principal с учётным логином и account permissions. Идентификаторы `OTTORESTART_OPERATOR_IDS` должны совпадать с логинами в credential map. Совпадающий `OTTORESTART_INTERNAL_AUTH_SECRET` задаётся только на сервере Next.js и OttoRestart backend; он не должен иметь префикс `NEXT_PUBLIC_`.
- Backend проверяет principal, выбранный JV/XL account и CSRF/Origin для каждого изменяющего запроса. BFF не пересылает браузерные cookies или произвольные actor/account headers.
- Aftercool M2M доступ может быть настроен отдельно: backend хранит только SHA-256 hash ключа (`OTTORESTART_AFTERCOOL_M2M_KEY_HASH`), разрешённые accounts и только `GET /api/restart/library/lookup`.
- Сессия хранится в подписанной HttpOnly-куке `ottorestart_session` (срок действия: 7 дней).
- Кнопка выхода из системы расположена в правом верхнем углу панели управления (топбар).
- Значения `OTTORESTART_AUTH_*` и `OTTORESTART_INTERNAL_AUTH_SECRET` передаются только серверным процессам и не должны иметь префикс `NEXT_PUBLIC_`.

## Backend and API

- OpenAPI document is generated by the authenticated FastAPI service; DTOs and browser client are in `features/api/`.
- The browser client calls the same-origin authenticated BFF at `/restart/api/backend`; it cannot be configured to call an arbitrary backend origin. The BFF forwards only allowlisted headers and preserves multipart request bytes.
- Mutating API requests require a signed principal, selected account, same-origin CSRF token, and allowed Origin. Idempotency keys protect accepted write commands.
- The backend stores discovery history, GTIN evidence, operations, QC, and durable jobs in PostgreSQL. New or unverified pool entries do not become eligible from checksum or import alone.
- Production status is derived from saved OTTO observations; missing fixtures or failed lookups do not establish absence. `GET` adapters require their explicit account-scoped feature flags and credentials.
- Product submission code and external write operations remain disabled. See `BACKEND_IMPLEMENTATION_PLAN.md` and [the runtime runbook](docs/OPS_RUNBOOK.md) for current gates.

### Initial import and discovery

The production Discover flow accepts an explicit `.txt`/`.csv` baseline. Preview is local; commit creates a durable run and returns `202`. The worker reads status, product and price for the selected OTTO account, then looks up the confirmed product EAN in the matching Aftercool account. Only a complete verified `NOT_FOUND_CONFIRMED` result routes a product to Direct OTTO; lookup errors, ambiguous identities, and missing evidence remain visible as unresolved.

Manual discovery is account-scoped and bounded to a maximum 16-day window. After an operator confirms the imported baseline, scans use the saved cursor and 48-hour overlap. Weekly scheduling is optional, disabled by default, and requires a confirmed baseline plus explicit server and account settings. These code paths require the separate migration and runtime setup described in the runbook; no worker or schedule is started by the application UI alone.

## Local development

Production views require the authenticated backend and show unavailable when it is not configured. The isolated DEMO routes below remain available only when explicitly selected; their synthetic records never merge with PostgreSQL records.

- `/restart` — synthetic dashboard, attention scenarios, recent demo batches and events.
- `/restart/batches` — search/list fixtures and create a synthetic batch with a Dry-Run preview.
- `/restart/batches/demo-jv` / `/restart/batches/demo-xl` — review and preparation flow for five demo scenarios.
- `/restart/ean-pool` — synthetic pool view; the button adds demo codes only.
- `/restart/review` — simulated preparation, standard-price scenarios, validation and approval.
- `/restart/queue` — session-scoped queue with local dry-run checks only.
- `/restart/history` and `/restart/settings` — mock audit events and account-scoped demo settings.

The pages described in the Phase 4/5 sections are DEMO-only and in-memory. They cannot publish or confirm ONLINE. See [Phase 6 demo prototype](docs/phase-6-demo.md) and [workspace API contract](contracts/otto-restart-demo-workspace-v1.yaml).

### Phase 4 — preparation and review demo

Open `/restart/review` on the existing Next.js preview, or `/restart/batches/demo-jv` / `/restart/batches/demo-xl`.
For the current SSH port forward this is usually `http://localhost:3002/restart/review`.
This demo needs only Next.js: no FastAPI service or API environment variable is needed.

- The DEMO banner identifies all fixtures, mocked prices and local AI title suggestions. The 70-character title limit and attribute rules are illustrative demo rules, not verified OTTO category requirements.
- Tabs cover candidates, preparation, approval, publication (disabled), and audit history. The comparison drawer supports edits, local illustration preview, validation, price refresh, and approval.
- Price is read from the simulated old SKU standardPrice adapter for the selected account, with integer-cent arithmetic: JV minus 1,000 cents, XL minus 1,500 cents. There is no Excel, Aftercool, or sale-price fallback.
- Supplied `DEMO-*` identifiers are deliberately not real GTINs. Reservation is confined to the session's demo pool. Repeated preparation keeps the reservation and never subtracts the discount twice.
- Server version checks reject stale edits. Approval re-reads the simulated price, captures an immutable payload and SHA-256 hash, and is invalidated by material edits or changed prices. The drawer includes a price-change scenario to demonstrate reapproval.
- Each browser gets a separate HTTP-only session in server memory. It expires after one hour of inactivity and resets on process restart. This is a single-process preview, not durable production storage.
- The API is `/restart/api/demo/*`; its separate contract is `contracts/otto-restart-demo-review-v1.yaml`. It does not use Phase 3's SQLite database, real batches, the working EAN pool, or OttoFlow services.
- Live source adapters, real AI, authenticated permissions and actual OTTO category/GTIN checks remain disconnected. `publishAllowed` is always `false`; no submission endpoint exists.

### Phase 5 — isolated queue demo

Open `/restart/queue`. It lists approved demo cards for the selected JV/XL account, lets you add immutable snapshots to a local dry-run queue, pause/resume processing, stop/start task intake, and cancel tasks before they run. A dry-run rechecks the approved version and simulated standard price; stale work is blocked and changed prices require reapproval. Successful completion records only a local demo result.

- Queue state is in-memory, browser-session scoped, and partitioned by account. There is no background worker or durable queue.
- Publication is disabled. Queue tasks do not call OTTO or Aftercool and cannot create online statuses.
- Contract: `contracts/otto-restart-demo-queue-v1.yaml`; details and limits: `docs/phase-5-demo.md`.

Validation: `tsc --noEmit --incremental false`. Phase 4 domain tests are in `tests/review-demo.test.cjs`; Phase 5 queue invariants are in `tests/demo-queue.test.cjs` and run against `demo-queue-service.ts` plus its compiled Phase 4 service dependency.

Requires Node.js 20.9 or newer.

```bash
npm ci
npm run dev
```

Open [http://localhost:3001/restart](http://localhost:3001/restart). The development server uses port 3001 so it does not collide with OttoFlow's port 3000.

### Production runtime

The isolated Compose stack builds the frontend in production mode and starts FastAPI without autoreload. PostgreSQL migrations are a separate explicit CLI operation. Redis, the worker, dispatcher, and Beat use opt-in profiles and remain stopped by default. Use the startup, TLS, backup, and recovery steps in [the runtime runbook](docs/OPS_RUNBOOK.md). Do not connect the Compose stack to OttoFlow's database, Redis, queue, or network.

### Offline release verification

Run `scripts/verify_offline_release.sh` from an egress-disabled verification runner with a disposable loopback PostgreSQL 15 server supplied through `OTTORESTART_TEST_DATABASE_URL` and the Restart Node dependencies installed from `package-lock.json`. The script disables external/write flags, blocks application/migration DSNs, runs backend and frontend suites, and does not start services. See the [release checklist](docs/RELEASE_CHECKLIST.md) for the database guard, evidence, recovery boundaries, and separately approved operational gates.
